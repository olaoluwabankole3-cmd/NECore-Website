Authentication and safe retries

  • ✓Use a scoped service API key in server-side requests. Workforce actions require appropriate authenticated roles.
  • ✓Reuse the same idempotency key for the same case-creation payload; a changed payload with that key returns 409.
  • ✓Send opaque customer references, not raw NIN, BVN, document images or biometrics.
  • ✓Use local synthetic fixtures for testing. Provider sandbox access is conditional; no real customer information.

Core endpoints

Method / pathPurpose
POST /v1/verification-casesCreate an individual verification case.
GET /v1/verification-casesList authorized institution cases.
GET /v1/verification-cases/{case_id}Read case status and risk tier.
POST /v1/kyb-casesCreate a business verification case.
GET /v1/kyb-cases/{case_id}/reportRead KYB completeness and risk summary.
POST /v1/verification-cases/{case_id}/risk-signalsRole-restricted risk signal ingestion.
POST /v1/verification-cases/{case_id}/review-proposalsAuthorized review proposal with a reason code.
GET /v1/verification-cases/{case_id}/auditRole-restricted case event history.

Handle errors explicitly

HTTPMeaningIntegration action
401Missing or invalid authenticationCheck authorized credentials.
403Insufficient permissionsRequest the appropriate institution role.
404Case not found or inaccessibleConfirm case reference within the authorized institution.
409Conflict or disallowed state transitionInspect current state or idempotency payload.
422Invalid requestCorrect fields against the contract.
503Service or dependency unavailableDo not infer approval; follow agreed retry and escalation policy.
